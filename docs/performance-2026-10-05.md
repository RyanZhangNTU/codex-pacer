# 资源优化与实时状态修复验证记录

记录日期：2026 年 10 月 5 日至 6 日。

**当前本地安装版本为 2.2.0（build 23）。事件发现及完成提醒在 build 22 通过实机验收；build 23 追加启动速率和过期数值修复，验证见文末。短暂的资源占用峰值仍未完全解释或解决。** 前面的章节保留初始候选及中间版本的数据，不能将不同阶段的结果混为一谈。

初始优化候选按用户明确要求，以 2.2.0（build 11）在本机覆盖安装测试。截至本记录覆盖的验收阶段，公开版本及更新源仍为 2.1.4；本次工作没有发布 Release、标签或更新源。旧应用和偏好设置快照保留在本机私有回退目录。公开发布仍须取得用户批准，并遵循[发布流程](releasing.md)。本次手动覆盖安装不构成 Sparkle 自动升级验收。

## 保留的数据与更新频率

常规本机 Desktop 事件订阅已改为在 Swift 的低优先级工作队列中运行。采集器校验有大小上限的协议数据，同时跳过对话正文、推理文本、工具参数与输出、问题与选项、回复内容。历史轮次只保留头部信息和条目数组的数量；仅提取当前轮次的事件元数据。修订号与发布方校验、补丁的原子应用、重新同步、内部审查任务排除等约束继续保留。轮次结束后释放条目存储。SSH 及本机 app-server-control 兼容路径仍沿用 Python 适配器。

持久化内容仅保留当前周额度周期。每个额度桶最多保留 2,018 个点，包括五分钟区间采样、首次读数和最新实时端点。常规缓存写入每三十分钟合并一次；切换账号、额度周期或 Codex 主目录，以及睡眠、正常退出时，会保存尚未写入的数据。加载旧的高密度缓存时，只在内存中压缩，不会因此立即写盘。实时任务、token 和额度的读取频率保持原有设置。

这些调整的明确代价是曲线分辨率降低，以及异常退出时可能丢失最多三十分钟的本地曲线历史。服务端实际额度和 token 数量不受影响。数据规模已有上限，使用原子写入的快照文件足够；另设日志或数据库会增加复杂度，目前没有证据证明能带来额外收益。

## 相同输入下的组件测量

基线源码来自优化前的工作区快照，包含此前已有的错误修复。两侧 CPU 测量都包含 JSON 解码与校验。回放使用完全相同的合成事件，并比较生成的运行事件是否一致；比较时排除随运行时间变化的时间戳。六组回放均产生等价事件。下表为每个补丁的 CPU 耗时中位数，Swift 使用优化编译。

| 测试输入 | 原 Python 适配器 | 原生适配器 |
| --- | ---: | ---: |
| 8 轮 × 32 条，仅正文增量 | 0.018 ms | 0.024 ms |
| 8 轮 × 32 条，正文与 token 数量更新 | 0.454 ms | 0.032 ms |
| 64 轮 × 32 条，仅正文增量 | 0.024 ms | 0.024 ms |
| 64 轮 × 32 条，正文与 token 数量更新 | 3.496 ms | 0.031 ms |
| 256 轮 × 32 条，仅正文增量 | 0.053 ms | 0.025 ms |
| 256 轮 × 32 条，正文与 token 数量更新 | 14.317 ms | 0.032 ms |

最小的纯正文增量案例，每个补丁约增加六微秒。较大的正文与 token 同时更新案例，耗时降低约 93–99.8%。**这些结果只衡量采集组件，不能解释为整个应用加速了相同比例。**

另一组未超过协议大小上限的压力测试包含 512 轮历史，每个旧轮次有 4,096 个空条目槽位，当前轮次只有一个条目，并发送八个 token 补丁；协议数据约 6.3 MB。两种实现交替运行三次，每 10 ms 采样一次进程物理内存占用：

| 仅采集器的压力测试指标，三次运行中位数 | 原适配器 | 原生适配器 |
| --- | ---: | ---: |
| 采样到的物理内存占用峰值 | 685.9 MiB | 14.7 MiB |
| 快照处理的 CPU 耗时 | 656.0 ms | 70.1 ms |
| token 补丁处理的 CPU 耗时 | 1,123.1 ms | 0.016 ms |
| 保留条目数 | 2,093,057 | 1 |

这组测试刻意放大历史数组保留的成本。它既不是整个应用的内存测量，也不能证明某一次实际运行峰值的原因。原生进程仍需接收有大小上限的协议快照；优化避免了构建和复制完整的历史对象结构。

## 曲线存储测量

使用一个合成的已验证账号及一个周额度桶，模拟七天周期最后一天的完整数据量：一天读取实时额度 2,880 次，即每三十秒一次。旧策略的写入量依据三个实际序列化缓存大小估算，**没有真的执行数 GB 的基线写盘**。新策略的写入次数和字节数通过临时缓存文件实测，包含结束时的一次强制保存。

| 指标 | 原策略 | 新策略 |
| --- | ---: | ---: |
| 每个模拟日的缓存写入次数 | 2,880 | 49 |
| 逻辑写入字节数 | 估算 2,103,788,160 字节（1.96 GiB） | 实测 3,599,599 字节（3.43 MiB） |
| 最终保留的曲线点数 | 20,160 | 2,017 |
| 最终缓存文件大小 | 786,616 字节 | 79,039 字节 |

逻辑写入量不等于 SSD 的实际物理写入量，也不包含文件系统写放大。更多额度桶、账号切换或重置周期切换都可能增加写入。该结果证明，在不改变实时读取频率的情况下，存储规模可以受到明确限制。

## 待回复提醒的验证与限制

Desktop 服务端的 `requests` 和智能体消息中非阻塞的 `questions` 是两种不同格式。目前同时观察本机及已启用 SSH 来源中的这两种数据。问题会产生持续提醒，但不会因此把仍在运行的任务错误显示为暂停；路由信息及经过哈希处理的标识仅临时保留。问题提醒不等待 250 ms 的 token 批量交付窗口。

打开对话不会自动解决问题。RPC 请求被移除时，相应提醒清除；消息问题在被移除、出现后续用户消息或当前轮次结束时清除。仅在 Desktop 界面中关闭问题浮层或发生超时的状态，不在此事件流内，因此提醒可能一直保留到出现可观察的清除条件。系统通知保留用户原有偏好。

已批准的刘海模式设计使用状态图标、单任务阶段文字或多任务数量，以及 k/M 速率缩写。待处理提醒归入对应的分页任务行，额度警告保留在右侧。

一次使用实际原生采集器的只读实时订阅，从 Desktop 消息元数据中识别到了真实的待回复异步问题。观察器使用独立的 IPC 身份，并正常订阅、取消订阅。它没有回答问题、批准命令、发送对话消息或中断任务。这批验证文件没有保存私有消息内容。

初始候选阶段的回归覆盖：稀疏历史、修订缺口与原子回滚、非阻塞问题、问题分阶段到达、回复／移除／结束后的提醒清除、跨主机路由、只监控的套接字请求、token／工具／完成事件交付、旧缓存压缩、合并写入，以及账号和重置周期隔离。该阶段 `make test` 通过了 185 项核心测试和 8 项灵动岛测试。arm64 验证构建没有编译器警告。随后 2.2.0 通用构建通过深度签名与架构检查；Xcode SDK 对 x86_64 汇总目标给出了警告，但最终包内两种架构的可执行代码均声明最低支持 macOS 14.0。

中英文隔离版 macOS 界面验证覆盖：折叠与展开时持续显示待回复提示、保留运行状态及速率、打开会话失败后保留提醒、明确解除提醒、连接警告，以及正常退出。一组刘海边界测试包含 120 个请求（显示为 99+）、约 60.6k t/s 的速率、一个来源警告和 100% 周额度，确认两侧内容仍可见；展开后的请求列表可独立于额度面板滚动。测试设备为 Apple M4 Max，系统为 macOS 27.0.1；没有在 Intel 硬件上实测。

另一次独立的 45 秒折叠态合成界面采样，包含两个演示任务，不运行额度 CLI 或 SSH。结果为平均 CPU 0.201%（单核口径）、物理内存占用中位数 53.2 MiB、进程磁盘写入计数增量为零。**这是仅界面的样本，不是实际安装版的完整进程树。** 该测试也早于最后一次刘海紧凑文字调整。

此前安装版采样和上述采集器基准的范围不同。组件结果不能证明整个应用低于 100 MiB，或空闲 CPU 低于 0.3%。实际额度 CLI、图形系统／WindowServer、远端主机均需按各自范围统计。原始本地记录和可重复运行的合成基准脚本保存在被 Git 忽略的 `output/performance/optimization-2026-10-05/`，不作为发布附件。

## 任务实时发现问题排查：10 月 5 日至 6 日

build 15–18 是本地诊断迭代版本。合成测试通过，并不能证明真实 SSH 路径正常。用户创建的约 26 秒任务，以及随后几次测试，暴露了更多任务发现、订阅确认和旧状态残留问题。仅看任务数量徽标不够，因为一个旧 A100 任务仍被显示为运行中；检查具体任务行，才能区分真实测试任务的完成状态与那条旧记录。**这些中间版本不能被描述为已经完整验收的修复。**

A100 的 SSH 命令／握手实测约为 1.36–1.44 秒，包含建立连接的时间。连接建立后，初始化、列举和读取 RPC 耗时为 86–169 毫秒。一次显式 Desktop 订阅在 6.8 毫秒内返回了小型测试任务快照。这些观察结果不足以用网络延迟解释应用中长达一分钟的等待。

本地任务完成提醒的问题，在修复前已经复现：终止条目的元数据释放后，紧随其后的状态补丁被误判为状态缺失，导致尚未交付的完成事件被删除。修复后保留已结束轮次的头部信息和条目数量；拒绝有问题的补丁时，保留此前已经有效的事件，并按顺序交付。完成记录的保留逻辑也兼容 Unix 时间戳转换产生的亚毫秒舍入误差，以及同一批数据中同时出现的有效开始与结束事件。

任务发现现在同时观察路由索引的原地写入和原子替换；文件被替换后重新建立监听，并在发布方要求时重新声明已有订阅。初始快照缺失时，会在限定次数内按时重试。发出订阅请求，不等于已收到并建立完整的初始状态。路由提示本身不会凭空生成任务的运行或完成状态。

build 19 将有数量上限的发现提示，通过现有 SSH 辅助进程的标准输入传递。远端 app-server 的元数据和事件作为运行状态的依据；Desktop 的远端视图只提供任务发现和待回复标记。确认运行中的元数据可以识别暂时没有新事件的任务，不必请求对话正文；确认空闲的元数据会抑制旧运行日志的回放，明确的结束事件则用于保留完成提醒。

build 19 已安装，但两次获准的 20 秒重复测试都未通过验收：运行接口已经报告任务处于 active 状态，安装版任务行却仍显示上一轮结束。一个被动 IPC 观察器没有收到该轮任务的发现广播；显式观察器自己的订阅／取消订阅广播，直到任务结束后才出现。连接成功、缓存快照更新，都不能证明任务能够及时被发现。这里暴露的是代码路径问题，不能作为网络延迟的证据。

对实际 1.38 MB 路由索引进行了优化后的30 次读取基准：索引发生变化时，解析 CPU 耗时中位数为 2.349 ms；未变化时，文件指纹检查耗时中位数为 0.032 ms。这些仍是组件成本，不是整个应用 CPU。正常发现由文件系统事件唤醒，不依赖周期性扫描对话日志，也没有新增状态历史写入。

## 后续进程树资源采样

采样包含 Pacer 主进程及其本机子进程，不包含共享的 Codex 桌面应用、WindowServer、GPU 活动或远端主机进程。各次任务、界面及网络状态不同，因此下面是实际观察记录，**不是仅替换代码、其他条件严格一致的 A/B 对照实验**。

波动相当明显。例如，build 15 的主进程峰值达到 309.9 MiB，平均 CPU 也较高；build 16 的主进程内存中位数则为 41.2 MiB。这些峰值的成因尚未建立。现有样本不能支持“平均 CPU、电脑总内存和磁盘 I/O 始终都改善了”的笼统结论。OS 磁盘读取计数增量为零，也不代表没有逻辑读取或命中缓存的文件读取。原始记录和采样器副本保存在被 Git 忽略的 `output/performance/local-build*/`。

build 20 增加了独立的远端索引发现。在 Linux 上，inotify 根据 SQLite 状态索引及其 WAL 文件的变化唤醒采集器；文件监听不可用时，每两秒比较一次文件元数据。**新增监听器不读取数据库内容，也不写入监控历史。** 发现请求会合并处理，并进行两次有次数限制的复查，覆盖“索引已经保存，但运行接口尚未变为 active”的情况。

相应套接字集成测试不提供 Desktop 提示或运行通知，而是原地改写索引文件，再检查是否能发现没有条目回放的运行任务，并保留明确的未读完成记录。后续实机检查确认索引确实更新，Linux 文件监听也已建立，但进一步暴露了下文的状态合并错误。自动测试通过，仍不足以单独构成验收。

build 19 的采样持续 120.008 秒，灵动岛保持折叠；本地当前任务仍在运行，并有一个待回复问题，远端测试任务处于空闲。采样期间没有额外诊断采集器或构建任务。主进程内存中位数为 76.8 MiB，进程树中位数为 118.1 MiB，与 2.1.4 旧样本接近。OS 读取和写入计数增量均为零，逻辑写入增加 37,080 字节。这不能证明磁盘完全没有活动，也不能证明各项资源均改善。统计不包含远端采集器及共享的界面／GPU 服务；每秒一次的采样还可能漏掉在两次观察之间启动并退出的短命子进程。

build 20 通过了 195 项核心测试和 10 项灵动岛测试，通用包也通过了深度签名校验。两种架构均声明最低支持 macOS 14.0；已知的 Xcode x86_64 汇总目标弃用警告仍存在。合成 Linux 事件格式测试覆盖了无关文件过滤、事件队列溢出和监听失效后的回退；当时，真实 Linux inotify 行为仍需 A100 实机确认。随后，在用户继续授权下安装了 build 20，但独立实机验收仍未通过。build 21 因此加入了有大小上限、仅在 Mac 运行的跟踪，用于定位状态合并错误。这两个版本均未公开发布。

## 已确认的状态合并错误：10 月 6 日

build 20 的独立检查仍出现“远端新一轮已经开始，界面却显示上一轮结束”。开始和结束时，索引元数据都有变化，辅助进程也持有有效的 inotify 监听。

build 21 的临时 Mac 跟踪确认：**运行中的元数据和条目事件，其实已经及时到达安装版应用。** 问题发生在第一个条目补齐轮次 ID 时：状态累计器被重新初始化，清掉了此前“已确认开始新一轮”的标记。随后，合并逻辑优先保留旧的已完成日志，覆盖了新一轮运行状态，也丢失了新的未读完成提醒。重复读取元数据有时会重新设置该标记，掩盖这个错误，因此出现过带额外诊断时似乎成功的情况。

加入“上一轮已完成回退记录”的回归测试后，旧实现出现六个失败断言。build 22 改为直接补齐第一个条目带来的轮次 ID，保留此前已经确认的开始状态，也不重置从中途开始估算速率的基线。该回归同时验证：没有此前确认依据的单独条目，仍不能覆盖一条已完成日志。

## 启动速率虚高与数值冻结：10 月 6 日，build 23

用户反馈新一轮开始时显示几千 t/s，随后数值长时间不更新。代码检查和旧实现的回归测试确认了三个相互叠加的问题：

1. 新一轮直接沿用上一轮累计计数，或把缓存的 `lastOutputTokens` 当成新一轮的生成量。上一轮的用量可能在结束之后才补齐，Desktop 的最新用量字段也可能仍属于上一次请求；将它们除以新一轮很短的已用时间，会产生启动尖峰。
2. 相邻报告不足 250 毫秒时，旧实现仍推进基线，却丢弃该区间的增量；连续密集报告可能一直不能形成新速率。相同计数的重复报告也会错误推进时间。
3. 15 秒过期只会让旧数值变灰，并不撤下它；折叠界面的普通时钟又是每 30 秒更新一次，因此数值会长时间停留。

旧代码的合成回放明确出现了首帧 **16,000 t/s**，随后 **3,216 t/s**；实际应测的新增量为 40 token / 2 秒，即 **20 t/s**。另一轮包含迟到的上一轮结算时，旧代码首帧为 19,920 t/s。这些是用于复现的确定性测试数据，不是用户模型的实测生成速度。

修复后的规则如下：

- 每轮、每次中途接入都从第一次观测到的累计计数建立基线；这一步没有可用速率。之后按累计输出增量和可测的活动时长计算，不再根据缓存的单次请求用量倒推初值，也不通过限制最大 t/s 来掩盖错误。
- 密集更新累计到至少 250 毫秒的有效时长再形成样本。重复计数不刷新有效期、不截短分母；计数回退或超过 120 秒的计数间隔会重新建立基线。
- 带有旧轮次 ID 的迟到用量不能改变当前任务。工具阻塞期间贡献已知的零速率；工具结束后必须有新测量，才能再次显示非零数值。并行工具等待区间只扣除一次；后台工具期间出现模型生成证据时仍计入生成时间。
- 15 秒没有新计数就撤下数值。界面为最早过期的样本安排一次性刷新；更新到来时替换该刷新，结束、切换来源和退出时取消。它不调用额度查询、文件扫描或 SSH。折叠栏继续保留任务状态；展开的悬浮模式显示采样提示。灰色合计只代表部分运行任务有新鲜测量，不再包含过期值。

`make test` 通过 201 项核心测试和 12 项界面测试，共 213 项，0 失败。覆盖缓存用量进入新轮次、旧轮次迟到报告、50 毫秒计数突发、重复计数、回退和乱序、工具等待，以及折叠界面无新事件时的到期刷新。测试夹具随后修正了日期转码的亚微秒精度边界，两个界面到期测试再次通过。既有任务发现与完成提醒回归均保留。
