# 额度轮播的空闲检查同步

两次原始 Windows 失败均落在 `IdleSchedulingChecks` 的四秒轮换检查：[#156 作业](https://github.com/RyanZhangNTU/codex-pacer/actions/runs/41614543261/job/125844578936) 与 [#154 作业](https://github.com/RyanZhangNTU/codex-pacer/actions/runs/41615550550/job/125848002229)。两份日志都通过了此前的 WebView2 和材质检查，没有记录失败时的时钟数或轮播阶段。

同步点存在明确缺口：测试在 300 ms + 450 ms 的稳定观察后，固定等 3400 ms，就假定 WPF 已执行淡出完成回调。计时器到期和 WPF 动画完成是两个调度步骤，固定等待不能证明后一步已经完成。两份 CI 日志不足以判断当时是否有持续泄漏。

集成时的本机复现还发现了早到回调：计时器先于 `Stopwatch` 的 3.65 秒边界触发，旧实现回到 hold 分支并再次安排计时器。第一版完成信号在这个 hold 分支误报完成，随后观察到唤醒数从 1 变成 2，淡出仍在进行。这是多余唤醒和错误同步，不能据此判为持续时钟泄漏。

`QuotaAlternationSchedule.AtDeadline` 同时接收实际时间和已触发的计划边界。计时器早到时只创建一次淡出，用 `BeginTime` 等到原边界；动画完成时直接进入已完成的四秒槽位，避免两个时钟的细小偏差再次创建淡出。迟到回调仍按原始时间轴跳过已过去的阶段。`QuotaCycleCompletion` 按完成的槽位通知，只有淡出时钟已清除、下一次唤醒已安排后才完成等待。

自然等待的复跑仍在 4.151 秒时超时，诊断为一次计时器唤醒、两条尚未完成的有限淡出时钟。测试现在保留真实的 hold 计时器和 WPF 时钟，在淡出创建后用控制器推进至结束，再等待其完成与释放信号，避免把 WPF 首次 timing tick 的延迟算成泄漏。这个推进入口只由测试订阅，普通窗口仍自然播放。

测试等待信号的期限仍为 3400 ms，继续检查唤醒数为 1、时钟数为 0、下一次期限已安排，以及快照、帧和空闲渲染计数。四秒槽位、350 ms 淡入淡出、30 fps 与全部原断言保持不变。超时、取消或完成都会解除订阅。受控时间回归覆盖 3.64 秒的早到唤醒、3.99 秒收到四秒完成信号，以及迟到回调；两家和三家服务均覆盖。

隐藏与恢复回归还发现，窗口隐藏后将额度动效关闭，重新显示时没有刷新动效偏好。显示路径现在会刷新收起栏，恢复原有数据的轮播；隐藏期间仍没有时钟或计时器。真实 WPF 空闲组和遮挡组的集成结果记录在集成 PR 中。
