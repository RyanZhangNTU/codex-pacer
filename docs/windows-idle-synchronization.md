# 额度轮播的空闲检查同步

两次原始 Windows 失败均落在 `IdleSchedulingChecks` 的四秒轮换检查：[#156 作业](https://github.com/RyanZhangNTU/codex-pacer/actions/runs/41614543261/job/125844578936) 与 [#154 作业](https://github.com/RyanZhangNTU/codex-pacer/actions/runs/41615550550/job/125848002229)。两份日志都通过了此前的 WebView2 和材质检查，没有记录失败时的时钟数或轮播阶段。

同步点存在明确缺口：测试在 300 ms + 450 ms 的稳定观察后，固定等 3400 ms，就假定 WPF 已执行淡出完成回调。计时器到期和 WPF 动画完成是两个调度步骤，固定等待不能证明后一步已经完成。现有 `AnimationLease` 在完成时会停止并移除控制器，`Step` 也会释放两条淡出时钟；目前没有发现必须修改产品轮播时序或修复持续时钟泄漏的证据。

`QuotaCycleCompletion` 只在淡出时钟已清除、下一次唤醒已安排后通知等待方。测试改等这个信号，期限仍为原来的 3400 ms，随后继续检查唤醒数为 1、时钟数为 0、下一次期限已安排，以及快照、帧和空闲渲染计数。四秒槽位、350 ms 淡入淡出、30 fps 与全部原断言保持不变。超时、取消或完成都会解除等待订阅；后续若出现真实泄漏，原状态断言和期限仍会报告失败。

按统一集成流程，本机只运行无窗口同步单元回归，连续 10 次通过。覆盖旧事件、重复事件、下一轮隔离、完成、超时、取消和订阅释放；未运行展示组，也不把它称为 CI 压力场景的十连通过。实际 WPF 空闲检查和完整展示矩阵留到集成阶段。
