# Development and data semantics

## Structure

Windows engine setup, isolated builds, protocol checks and shared Core boundaries are described in [Windows engine development](windows-engine.md). The [WPF shell guide](windows-shell.md) covers desktop tests and the unsigned CI ZIP. The root SwiftPM package builds the Windows engine and UI adapter; the shipping Mac app continues to use the native package.

- `native/Sources/PacerCore`: quota decoding, task lifecycle, rate estimates, source discovery, transport, completion retention and window geometry. Claude quota, web and cloud clients receive credentials, account identity, storage callbacks, HTTP, streams and clocks from the host. Their validation, account isolation, retry and cancellation rules stay here.
- `ActivityNavigationState` captures source and ending tokens before a host opens a task. `HostApplicationTrackingState` retains opaque host facts and bounds scans; `ApplicationLifecycleCoordinator` owns module/source changes, work cancellation, sleep/wake plans and cleanup within one 650 ms deadline. The hosts keep application activation, native timers and OS power events. `IslandInstanceLock` is a MacSupport host service.
- `native/Sources/PacerMacSupport`: Mac child processes and byte readers, file metadata and replacement, application/CLI discovery, Pacer-owned credential storage and packaged resource lookup. It also assembles Claude's production clients, owns Keychain operations and the legacy cipher, and supplies URLSession data and byte-stream factories. Hosts supply these through Core protocols and callbacks.
- `ClaudeDesktopRecords` reads bounded account/session metadata through injected directory roots and file services. The Mac root is `~/Library/Application Support/Claude`; Windows hosts choose the active Desktop data folder as described in [Windows shell](windows-shell.md#claude-desktop-data-folder). Native application and CLI discovery stay in MacSupport. `Activity.swift` and `RuntimeStreamStatus.swift` hold shared values; the existing local reader and timestamp parser live in separate files.
- Mac and Windows use the same `ActivityLogWatcher`, `ClaudeActivityMonitor` and `DeepSeekActivityMonitor`. Core owns watch limits, debounce, flush, catch-up, baseline and publication; hosts supply raw file events, loopback sockets, helper processes, live-writer facts and clocks. Helper stdout has one ordered consumer with backpressure; stdin EOF and termination escalation belong to the host. Windows socket reads wait on readiness or a separate cancellation event.
- Claude hook configuration, migration, conflict handling and uninstall are shared. MacSupport supplies the existing `python3` command format, owner/symlink validation and atomic 0700/0600 writes. Windows supplies the packaged Python runtime, command serialization and file-handle ownership checks described in [Windows Claude runtime](windows-claude-runtime.md). Telemetry's HTTP limits, OTLP projection and bounded gzip decoding are shared; `CGzip` vendors only zlib 1.3.2 inflate/checksum sources with isolated symbols and an upstream receipt.
- `RealtimeActivityMonitor` merges Codex local, SSH and Remote Control results on both hosts. `DesktopCollectionSession` owns handshake deadlines, snapshot retries, batch flushes, heartbeat and EOF ordering. MacSupport supplies Unix sockets, kevent and routing watches; Windows supplies authenticated named pipes and writer proofs. Source changes and shutdown share the 650 ms budget, and late callbacks carry the connection identity.
- Process ancestry, PID reuse checks, rollout-holder selection, Claude live-record parsing, SSH argv validation and runtime diagnostic redaction compile in Core. Mac process inspection, bounded SSH capture and diagnostic file permissions stay in MacSupport. Windows uses the same ancestry checks with native process instances and Restart Manager/file-handle facts. Helper programs are shared constants; each host owns Python launch and stdin EOF.
- DeepSeek's summary and session-fingerprint programs are bundled once under Core Resources. Native browser drivers evaluate these resources in an isolated script world; the shared resource contract checks the origin and script names without freezing script hashes.
- Shutdown, sleep and source-change cleanup share a 650 ms deadline, including quota-history flushes. Completion signals can time out even when a task ignores cancellation. The Mac child adapter escalates to SIGKILL after 500 ms independently of pipe cleanup; the final app-exit handler can also terminate registered Pacer-owned children without waiting for their actors. Quota history uses atomic file replacement, so interrupted cleanup can lose pending samples while leaving the last committed file intact.
- DeepSeek balance coordination reserves its single flight before publishing the pending state and starts the reader after that publication completes. An immediate reply cannot arrive before pending and leave the display refreshing. A source change or shutdown during publication revokes the reserved attempt before IO starts.
- File metadata describes the directory entry without following symbolic links, matching completion-store validation, authentication fingerprints and DeepSeek discovery/creation dates. DeepSeek cursor reads explicitly follow links to obtain fresh target size and modification time.
- `AgentProvider` / `ProviderModules`: provider identity, bounded installation detection and automatic or explicit module choices. Claude and DeepSeek collection/quota adapters feed the shared activity, performance and completion model.
- `native/Sources/CZstd`: the decompression half of the BSD-licensed Zstandard library, built without assembly, legacy formats or tracing, for DeepSeek Harness session logs.
- `native/Sources/PacerIsland`: SwiftUI/AppKit presentation, settings, notifications and native glass.
- `PacerCore` presentation models own compact-bar visibility, quota readings, account/history labels, DeepSeek dial and spend summaries, and wallet notice thresholds. `IslandModel+Presentation` supplies their inputs; Mac views draw the results and dispatch native actions. Typed inputs avoid converting Mac state to JSON.
- `ActivityApplicationState` owns activity merging, visibility, completion retention, pending replies, per-provider notice baselines, latest TTFT and cached task grouping. Mac and Windows supply observed facts and publish its snapshot. `ActivityTaskPresentation` supplies rows, header state, source labels and pagination; hosts map glyphs and colors. Turn durations use the same `CompactDuration` wording. Demo module filtering applies to the synthetic snapshot without changing observed-data filtering. The state publishes the earliest rate, retention or turn-time display deadline; that wake-up refreshes presentation without starting collection or quota requests.
- Windows prewarms Claude's private blank browser controller before enabling the quota bridge. Environment and controller startup have a separate 60-second budget; cookie inspection keeps its 20-second budget. Concurrent starts share the same preparation, and cancellation or profile clearing releases the pending controller. Browser tests record only startup stages and durations, with no cookies, account identity or profile paths.
- `native/Tests/PacerCoreTests`: regression coverage for lifecycle, privacy, transport, rate calculation, account isolation, retention, geometry and preferences migration, with the entire target compiled on Mac and Windows. `native/Tests/PacerMacSupportTests` contains Mac/Unix IO integration coverage, including singleton locking.
- `native/Tests/PacerIslandTests`: presentation-model coverage for conversation opening and acknowledgment persistence, provider/quota dashboard display, compact components, rates and width measurement.
- `scripts/native`: isolated local build/test entry points.
- `scripts/performance/benchmark-events.py`: controlled Desktop IPC event replay; see [performance checks](#performance-checks).
- `scripts/release`: native signing, notarization and publication.

Shared presentation enums encode their existing string values. Compact warning and DeepSeek alert kinds, DeepSeek connection actions/colors, compact providers/options and quota/budget verdicts reject unknown JSON strings with `DecodingError.dataCorrupted`; the compact byte projection returns `nil` for such requests, as it did for invalid option strings. Optional actions and verdicts still accept absent or null values. Reading Mac preferences keeps the existing defaults (stage, remaining quota, and no ring for a present unknown or empty ring choice) without rewriting saved values. A failed native compact projection returns an empty presentation, and a missing or unknown component produces a hidden placeholder. The native cache keeps separate entries for requests with and without status text.

Use Xcode 26 or newer. Test/build commands, applicable manual checks, updater isolation and publication are defined in the [release workflow](releasing.md#validation-scope). Resolution follows `Package.resolved` without refreshing unchanged dependencies. The executable remains `CodexPacerIsland`; the user-facing app is Codex Pacer. `native/Info.plist` is the production version source.

Development builds are ad hoc signed. The build prints its app path; open that app in Finder for UI checks. Exit the installed app first: all copies share the same singleton lock. Demo arguments `--demo` and `--demo-completion` supply labeled sample data (`--demo --demo-subagents` supplies one parent and three synthetic agents; `--demo-claude` adds a Claude task that follows the demo stage, so the badge orbit shows both providers until the completion stage leaves Codex running alone; `--demo-deepseek` adds a DeepSeek task with a turn cost; `--demo-cloud` adds a Claude cloud Project's coordinator and threads, starting on the waiting stage; and every demo has a sample DeepSeek wallet and week of spend) without querying Codex. Demo keeps its task snapshot when Settings change. Demo tasks, pending requests and unread endings follow the saved module switches. Automatic module choices use synthetic installations; explicit disabled choices still hide their samples. Demo opens expanded and pinned; `--demo-collapsed` starts with the collapsed bar. Each provider receives its own sample quota (Codex weekly-only with banked resets, Claude with 5-hour and 7-day windows). `--demo-notch` supplies hardware-notch geometry for screenshots on virtual displays; production mode uses the screen’s own safe areas. Command+1/2/3/4 switches synthetic thinking/tool/reply/completion events through the same runtime projection. Demo clicks open an explicitly labeled sample destination, never a real conversation. `--expanded` starts with the island open. Command-line diagnostics `--diagnose` and `--diagnose-events --observe-seconds 20` report protocol/counter availability without credentials, account identity or task text. Add `--desktop-only` to verify local runtime and Desktop attention/discovery without starting SSH helpers.

## Data and calculation

Codex quota comes from a dedicated read-only app-server connection using `account/read` and `account/rateLimits/read`. No turns are created or resumed. Missing data remains unavailable. Multiple service buckets take precedence over a legacy single-bucket response. Credit and reset details are read from the service, without API-price conversions.

Mac and Windows use the same `CodexQuotaCoordinator`, `ClaudeQuotaCoordinator`, `DeepSeekBalanceCoordinator` and `ClaudeCloudCoordinator`. Hosts inject clients, history storage and web readers, then publish immutable states. `PrioritizedClaudeQuotaConnection` keeps Mac's passive status-line, web-session and compatibility order, including passive reads while the network source is throttled. Host source changes revoke publication before awaiting cleanup; a late read cannot publish, advance to another source or release a replacement's slot. Cleanup keeps the shared 650 ms deadline.

Quota polling retains Mac's 30-second expanded and 120-second collapsed base intervals, failure count capped at four, and 480-second maximum expanded failure interval (600 seconds collapsed). DeepSeek retains 60/300-second active/idle intervals and its existing failure backoff and post-turn grace. A sleep replacement carries the previous attempt and failure state. History stays bound to verified quota accounts or the selected DeepSeek billing source; a same-session challenge preserves wallet history and a new session clears it. Mac keeps its existing history preference keys, paths and numeric encodings. Cloud unread endings survive a disabled view for the same verified session, but a different verified scope or sign-out purges that account's retained endings.

DeepSeek history also stores a 128-bit HMAC-SHA256 credential tag. A locally generated 32-byte salt shares the history's protected storage: a separate Data value in the Mac preference domain, or `history-salt-v1.bin` beside Windows' global `history-v1.json`. Successful reads use the exact API key sent with the request, or the existing web token digest after the page verifies that its token stayed unchanged through the request and digest calculation. Credentials and unsalted identities never enter history or presentation snapshots. Changing a verified credential starts fresh history; the same credential retains history across restarts and log-home changes. The existing eight-day retention and source-change cleanup remain in place.

Source-compatible legacy history without a tag adopts the first successful credential; earlier ownership cannot be recovered. Missing or damaged salt starts a new binding. A salt read or write failure keeps the live balance available while withholding unverified history and preserving its last saved bytes. Malformed saved tags reject the history instead of becoming legacy data. Read-only quota diagnostics cannot call history or salt storage.

Windows `scripts/windows/check-engine-idle.py --real-data --quota --seconds 300 --engine <path> --output <path>` opts into read-only quota diagnostics. It disables history and credential writes, uses only passive Claude status-line metadata, and reports numeric refresh/connection counts and CPU without saving protocol bodies, source paths or credentials. Codex uses its read-only app-server connection; DeepSeek can read an already stored Pacer balance key, while its browser source remains unavailable without a host. This mode does not sign in or open a browser. Omitting `--quota` retains the existing collector-only diagnostic mode.

Some legacy CLIs reject the rate-limit parameter object with `-32600` and `invalid type: map, expected unit`. Pacer retries that specific schema mismatch once with the `params` field omitted and keeps that request shape until the connection closes; a new connection probes again, and `--diagnose` reports whether the legacy shape was used. That shape cannot request reset-credit details. Other RPC errors are surfaced without this retry, and the fallback retains the same account verification and quota decoding. A CLI without account-routing metadata can report quota but cannot establish an account scope for history.

### Provider ownership and Claude sources

`AgentProvider` distinguishes Codex, Claude and DeepSeek. Existing Codex activity keys stay `host:UUID`; Claude keys are `claude:host:session` and DeepSeek keys `deepseek:local:session`. Parent/agent grouping cannot cross provider or host. Claude agent IDs may be bounded opaque identifiers rather than UUIDs. Display metadata, late numeric updates, input/approval requests and retained completions use the same provider-qualified identity. Turning one module off releases only its collectors, work and reminder baselines, preserving the other module's tasks and completion cards.

`ProviderModules` stores automatic, enabled or disabled choices. Absent/malformed settings default to automatic, which detects known application and executable locations without launching a provider or inspecting authentication. Explicit choices override later detection; restoring automatic does not freeze the detected value in preferences. Existing Codex display, quota-window and cache choices remain intact. Claude has its own quota-window selection and history directory. The shared singleton lock and production bundle identity remain unchanged.

The expanded task region contains both enabled providers regardless of the dashboard quota period. Mark All as Read, to the left of Pin, acknowledges every displayed unread ended family across all task pages through `CompletionInbox`, including its ended descendants. Running or waiting families, outstanding replies/approvals and hidden sessions are excluded. The action does not navigate or answer a request; source-scoped dismissal persistence prevents reader replay or relaunch from restoring the same ending, while new turns remain eligible. Before the panel controls, the task header shows one button per enabled module whose desktop app resolves (`com.openai.codex`, `com.anthropic.claudefordesktop`), in the provider color with its generic glyph, whether or not that module has a task. It activates or launches the app and opens no conversation; a CLI-only module shows none. Lookups run off the main thread at start, after a Settings change or a failed open, and at most once a minute when the panel expands. *Show App Buttons* in General (`showAppButtons`, default on) hides them; the 3.2.2 What's New note offers the same switch. Demo shows a button for each enabled module and opens a labeled sample instead of an app. Settings → Appearance → Expanded Quota saves `expandedQuotaStyle` as `split` (default, including absent or unknown values) or `classic`. The choice applies through the existing Settings update and survives relaunch without changing quota sources or collapsed-window choices. Classic retains the previous two-provider weekly rings with 5h underneath and the single-provider pair of 5h/7d rings. In Split Ring, each enabled provider has one quota ring. When its account bucket reports a 300-minute window, the ring splits into a shorter upper 5h arc (132°) and a longer lower 7d arc (204°), separated by two 12° gaps. Both periods show their own percentage and reset countdown inside the ring, with independent pace ticks along their own arcs. This layout also applies with one provider enabled. A missing 5h window leaves a weekly gauge: one 290° arc from 125° that opens at the bottom, with the period label in the opening, so even a full arc keeps two ends. A reported 5h window with unknown usage stays split with a dashed unknown segment. When only Codex is enabled, its primary `codex` bucket has no 300-minute window (in Split Ring, no 10080-minute window either) and at least one reported quota value, positive duration or reset date, the previous quota bars render all actual snapshot buckets/windows, including nonstandard and unspecified durations. Missing, empty or wholly unmeasured snapshots do not establish this exception or a weekly-only account. Source and freshness remain available in Settings and hover help; stale indicators and errors remain visible, and stale/error bars have no live pace. Each ring encodes remaining quota; a white tick marks the remaining-time fraction from the actual duration and reset date, so an arc past the tick is ahead of an even pace. Fresh quota adds an ahead/on-pace/fast verdict using the existing 85%/115% pace thresholds; stale or failed quota has no verdict. Each period's label and value turn amber at 15% or below or when that period spends fast; only the 5h arc turns amber as well. With two providers, split-ring pace verdicts stay in hover help and accessibility text, and a weekly gauge keeps its verdict beside the provider name. With one provider whose quota is not wholly unavailable, the ring sits at the row inset without a caption, and details beside it show each period's verdict, pace percentage, compact reset moment (the time today, the weekday within six days, otherwise the date) and forecast; the 5h and 7d groups face their arcs, and a weekly-only account shows pace, reset and forecast rows. `QuotaWindow.projection` extends the average spend since the window opened to its reset: the remainder at reset, or the time until it runs out, shown in amber. Within the first 5% of a window it reports too early, and stale or failed quota has no pace or forecast. Missing values remain unknown independently. There is no period switch: a 5h choice saved by earlier development builds is ignored and removed on the next Settings save, and collapsed-window choices stay independent. In Split Ring, weekly-only accounts show the 7d gauge without an extra 5h or PRO placeholder; Classic retains its original placeholder where applicable, and there Codex-only accounts without a five-hour limit keep the bars. The model’s historical `proOnly` availability still describes a missing-window state, not a detected paid plan. History charts and full quota/Credit/reset details stay in Settings with independent provider source, freshness and warning states. The whole Quota details header toggles its section as a native button, including keyboard and accessibility activation. Expanded provider names identify Codex and Claude. Rings use a thin quota stroke and pace tick with a central quota value and compact reset countdown; source, full reset dates, bucket names and update age are available on hover and in Settings. The collapsed bar combines task counts, available measured TPS and attention, but does not add or average independent quota percentages. The collapsed quota value alternates between enabled providers every 4 seconds in provider color, with a Core Animation crossfade that wakes no app code and pauses while occluded; a provider without a value leaves the alternation, and one enabled or known module shows its own value. Optional quota rings show both remaining quotas at once, Codex outside and Claude inside. Full provider names remain in accessibility/help text. One service's quota failure cannot replace the other service's data or error state. Source reset cancels old quota work and rechecks generation after every suspended read; changing the Codex directory resets Claude only when enabled SSH discovery actually uses that directory.

Production quota reads prefer a fresh status-line sample with a matching hashed account scope, then `ClaudeWebQuotaClient` using a session from Pacer's dedicated `WKWebsiteDataStore`. Connect opens Pacer's own claude.ai WebKit login window; the user completes ordinary website sign-in and any challenge. Production performs zero reads of another application's Keychain/Safe Storage, including during Connect, and imports no Claude/Safari/Chrome cookies. Session cookies are managed only by WebKit; quota requests receive them transiently in memory without writing a parallel JSON/cookie store or logging values.

**Sign-in windows.** Claude's and DeepSeek's sign-in windows show the website under a strip in the provider's color that says what signing in shows, with Refresh and Later; the host is in the window title. Each records the session present at open as a one-way fingerprint: Claude's session hash, checked again whenever Pacer's cookie store changes or the page finishes loading, and a SHA-256 digest of DeepSeek's page token, computed in the isolated script world after each load and once a second while the window is open, so Swift never receives the token. A fingerprint different from the one at open is a new sign-in: the strip turns green with Done and the window closes after 1.5 s. Closing it any other way (the close button, ⌘W, Later, Done or ⌘Return) also completes while a session is present, so a website sign-in is never lost; it counts as new only when the fingerprint differs. A new Claude session clears the saved organization and a new DeepSeek token starts a new balance history, while the session the window opened with is only read again with the existing choices. Every completed DeepSeek sign-in replaces the outstanding balance read, so a result from before sign-in cannot overwrite the new wallet or block its refresh. Without a session the window closes without asking, and Done and ⌘Return leave it open. Third-party sign-in pages open in their own windows, which close with it.

The Web adapter issues read-only GETs for account, organization and usage data. It verifies session/account/home/organization binding and rejects redirects, mismatched authentication and HTML challenge responses instead of treating them as quota. A known selected organization must belong to the authenticated account; multiple organizations require explicit selection rather than choosing the first result. Session/account/organization changes invalidate cached identity and in-flight results. Expiry or a website challenge requires a user-visible sign-in/verification action; startup and refresh never open that window automatically. Network failures and 429 responses remain retry states. Valid `Retry-After` backoff is bounded and scoped to the matching session/binding; retained quota keeps its original capture timestamp.

Without an established WebKit session, `ClaudeQuotaClient` remains a quiet compatibility fallback for Pacer-owned OAuth cache entries or explicitly supplied environment/file credentials. The own-cache item uses its default creator ACL, without relaxation or synchronization; no production fallback reads a foreign Keychain item. This is not a Data Protection Keychain entitlement workaround or the primary connection/import flow. A usable existing token remains account/home/organization bound, and its expiry/revocation does not trigger an automatic authorization dialog. OAuth compatibility requests keep verified-provider preference and account/token-scoped bounded Retry-After behavior.

Normal relaunch may reuse a still-valid WebKit session; this does not establish indefinite website access or persistence across every binary/signing/profile change. Both quota integrations are private and version sensitive. Settings, errors and logs contain no cookie, OAuth token, raw response or account identity. Desktop history is not an automatic quota fallback. Missing resets disable pacing/current-cycle recording; missing Credit balances and reset-bank data remain unavailable.

Claude task collection uses a bounded native incremental reader, optional additive hooks and a loopback-only OTLP HTTP/JSON receiver. Transcript text is reduced to presence/kind markers before activity projection; prompts, response content, tool arguments/output and account attributes are not retained. Hooks supply start, tool and attention boundaries. Claude Code's `PermissionRequest` and `permission_prompt` Notification carry no tool ID, so the adapter keeps up to 16 started tools per thread as CRC32 checksums of name and input (no text) and assigns the request to the matching waiting tool; that tool's own end clears it, a notification arriving after the tool ended is dropped, and a question's permission shows as a reply rather than an approval. Stop/SubagentStop observers only record an attempted stop. An explicit transcript `stop_hook_summary` completes a turn only with `preventedContinuation == false`, explicitly empty `hookErrors` and `hookAdditionalContext` arrays, and ownership established by the prompt/parent-UUID chain. The boolean alone is insufficient; missing ownership after a gap never falls back to a timing guess. This prevents another Stop hook's continuation from retiring the current turn prematurely. Claude Desktop's next-step box can instead end the turn from its own tool result, after which no `end_turn` or stop summary is written: an owned single tool-result record whose `mcpMeta._meta["claude/endTurn"]` is `true` completes the turn the same way and leaves a reply reminder until the next prompt, an interruption or the session's end. Only that boolean is read; the box's text is not. A baseline replay restores the completion but not the reminder, since the box may already have been answered, and the ending sends no notice of its own because the reminder already did. A foreground Agent's typed completed result can end only its observed owned child. A forked Skill such as `/code-review` runs in a sub-agent and reports `forked` instead: a successful foreground fork counts as that completed result and a `background` fork as an asynchronous launch; inline skills name no child. An asynchronous launch stays active until an engine-authored background notification proves a terminal status for the exact stored child/tool pair. Only the reserved direct header is projected, under the engine origin gate; summary/report text is opaque and never retained. Child ownership stays bound to its own observed run even after the parent starts another prompt. Unstarted internal-agent hook events do not create public tasks. Explicit engine interruption markers are accepted only for the matching active owned prompt without human-message provenance, with the typed-prompt marker preventing spoofing; only marker presence is retained. Missing files/gaps leave activity unconfirmed without inventing interruption. Initial log/spool baselines retain historical cards without replaying completion reminders, including boundaries split across publications. A baseline tail still running when the baseline ends becomes unconfirmed if its last evidence is more than 15 minutes old; a younger one is checked again by the existing one-minute maintenance pass once it reaches that age, unless newer evidence or an ending arrives first.

Claude Desktop can copy SSH/WSL transcripts into the default local Claude home. A unique validated SSH/WSL context in the active Desktop account's bounded metadata excludes that copied session and its children before bounded file selection, so mirrors cannot occupy real local reader slots or directory watches. It also removes the erroneous Local completion card and displayed notice. Custom Claude homes retain their own local observations. Ambiguous or missing metadata leaves source ownership unchanged; provider/host-qualified activities remain independent even when their session UUIDs match. Exclusion metadata is refreshed during discovery and cached for ordinary publications.

Both local and SSH transcript readers retain up to 512 ID-only prompt anchors and parent links, including unresolved links. Desktop can append a record before its parent, such as an attachment before its tool result; later descendants resolve through that link once the parent arrives. A descendant read while its parent is still missing, even a final response or stop, is emitted unowned as before, and its owned rows wait under the missing ID, keeping at most 16 IDs and the newest 64 rows for each. When the parent arrives, they are released with the proven prompt in file order and keep their original historical flag; the state model still ignores an ending older than newer evidence or belonging to another turn. Walked links are compressed onto the prompt, missing ID or ownerless root they reach, so a long unresolved chain costs a constant number of lookups per record, and an unresolved record is converted once. A repeated record keeps ownership it has already proven. Proven prompt anchors keep long ordinary chains readable after earlier records expire. Missing, evicted, foreign-session or cyclic parent chains stay unowned; a new prompt is never used as an ownership fallback, and reader gaps or file replacement reset the context and drop waiting rows. Ordinary appends are drained sequentially in bounded chunks. The 512 KiB initial and 128 KiB append budgets are per-read limits, not evidence of lost data. Remaining complete records/backlog schedule another drain and preserve the parent-ID chain through large Desktop attachment bursts. A real over-budget attachment/gap still invalidates ownership and leaves terminal state unconfirmed. Historical-baseline publication waits for its bounded drain to finish; this implementation does not itself establish acceptance of every Desktop burst in a packaged app.

An unowned projection also keeps `unownedTurn` on a legacy `user` record's generated prompt row, even though that row uses its own UUID rather than the deferred-owner placeholder. Until its missing ancestor proves ownership, it cannot start a turn, replace a current turn or revive a completed task. The native and SSH readers apply the same rule.

Claude task rows reuse the Desktop application lookup for 60 seconds when deciding whether a conversation can open; the actual open still resolves it afresh. The Claude profile used for account binding is reparsed only when its file signature changes. The native Claude reader checks cursor existence, inode, size and readability before opening a file. An unchanged readable EOF cursor skips open/seek/empty-read work; buffered complete records, new bytes, replacement and disappearance still use the normal bounded path. Task grouping in the UI model is reused only while its activity snapshot is unchanged. Overview calculations reuse those groups with the exact current Date, so the freshness boundary, retained TPS and lifecycle projection keep their existing precision. These changes reduce repeated work without changing collection cadence or asserting a measured whole-app energy reduction.

Native transcript context and activity projection share one bounded JSON document per line; only sanitized fields and identifiers survive that line. Selected project/subagent directory watches remain attached between ordinary reads, allowing new files to trigger discovery immediately. Claude's watcher bounds are 32 files plus 99 parked directory descriptors; Codex retains its existing four-directory bound. The SSH helper likewise decodes each transcript line once. Known-file inotify appends mark that cursor dirty without a project-tree scan; create/delete/move, self events and overflow still reconcile the bounded inventory. None of these paths adds a polling timer or changes first-output/lifecycle timing.

Matching numeric OTLP `llm_request` evidence supplies exact request duration, output-token accounting and reported TTFT. Current Claude Code request spans carry `session.id` and `request_id` but no `prompt.id`; such a span binds to the session's current turn only when its `llm_request.context` is `interaction` and its start is at or after that observed turn start, without a pre-turn tolerance. Background requests and late spans from an earlier turn stay unmatched. An observed fallback pairs unique authoritative transcript request/message counts with a complete prompt/tool-result-to-model-output window, excludes confirmed tool waits and settles only after a verified owned stop. It is marked `observedRequest` and remains an estimate; a same-request OTLP sample outranks it regardless of delivery time. An actual interactive MessageDisplay callback with an explicit matching prompt ID, validated turn/message IDs and adapter-owned provenance, `final == false`, `index == 0` and nonempty-text presence may establish client-observed first-output timing. Desktop SDK, `-p` and other final-only delivery paths cannot establish that proxy; absent numeric TTFT it remains unavailable. Neither full transcript text nor display delta content is retained. Numeric measurements may enrich only the matching observed turn and do not create a task, replay a reminder or extend completion retention.

Claude holds each displayed batch until its hooks return, so Pacer registers the MessageDisplay observer only when its own telemetry is not configured, and then as an `async` hook. Bounded JSON is parsed once; only the top-level event and final flag can reject a display call, so nested tool-result fields cannot suppress lifecycle events. Structurally ineligible MessageDisplay callbacks return before acquiring the hook-state lock or rewriting state/spool files. An eligible first partial callback must carry its own matching prompt ID and preserves child/parent routing. Missing prompt ownership stays unknown; it never falls back to the current Hook state. Native and SSH ingestion require the updated adapter's ownership marker, so legacy inferred display records cannot seed latency. Duplicate, previous-prompt and post-completion callbacks cannot move first-output timing or reopen a completed turn. Hook identifiers reject trailing newlines as well as other characters outside the bounded identifier grammar.

Local and SSH OTLP receivers accept HTTP/JSON with identity or gzip encoding, each bounded to 1 MiB compressed and expanded. Truncation, CRC failure, trailing data and expansion overflow fail without publishing frames. Typed AnyValue fields remain distinct; integer tokens and nanoseconds are normalized exactly from bounded decimal/exponent forms before range checks, so fractions, booleans and nonfinite values cannot become token counts. Invalid explicit span values shadow resource defaults; a present invalid primary request/model key cannot borrow its alias. These checks preserve correlation and do not establish a successful turn ending.

Local hooks need no Settings action: each Claude source start calls `ClaudeHookInstaller.ensureInstalled`, which skips a missing Claude home, returns without writing when the installation is current, migrates outdated Pacer entries in place and reinstalls missing required hooks. Settings shows the result as one status row with Retry on failure. Saving the Claude module as explicitly disabled uninstalls Pacer-owned entries; automatic detection flips never do.

Claude's self-reported progress ring is off by default (`claudeProgressRing`). While it is on and Pacer manages the hooks, the engine keeps the switch file `pacer/progress-ring` in the selected Claude home; it writes nothing until Pacer's hook folder exists and removes the file when the switch, the module or the home changes. The file holds `tool` (an older `on` is upgraded), and the engine brings the hooks current whenever its contents change. In tool mode the installer writes Pacer's Claude Code plugin into `pacer/plugin`: a local marketplace named `pacer` whose one plugin runs `claude_progress_mcp.py`, a stdio MCP server with the single tool `report_progress`. It lists that marketplace in `extraKnownMarketplaces`, enables `pacer@pacer` in `enabledPlugins` and pre-approves `mcp__plugin_pacer_pacer__report_progress` in `permissions.allow`; the installer records its additions and the previous plugin enable value in the installation manifest's `progressPlugin` ledger. A marketplace named `pacer` that points elsewhere causes setup to fail without replacing its settings. Turning the switch off or uninstalling restores only recorded values that still match Pacer's installation. Existing permissions, unrecorded entries and user edits are preserved; repointing the marketplace also preserves its dependent plugin and permission settings. Claude Code loads plugins when a session starts, so the adapter records at `SessionStart` whether the plugin was enabled, and only such sessions are asked to use the tool. For a typed main-thread `UserPromptSubmit` in such a session, the adapter prints one fixed `additionalContext` line, worded as the user's request, asking for an estimate with the tool with the first tool calls, whenever there is progress and before stopping to wait for background work, in the same batch as other tool calls. The `PreToolUse` hook reads the call's `percent` and writes a spool row of kind `progress` holding only the integer; the server only acknowledges the call. Another word in the switch file selects marker mode, used for comparison: the line then asks for a leading `⟦NN%⟧` on every message, the installer registers the background (`async`) `MessageDisplay` observer, which reads the marker from each message's first displayed lines and returns them without it as `displayContent`, and `ClaudeActivityRecord` also decodes at most 48 bytes from the start of each persisted assistant text block (`JSONFieldView.stringPrefix`). Markers inside the text, in thinking or in user messages are ignored, and values above 100 are dropped. Estimates apply to a verified current turn before the newest-evidence rule, because one can be read after newer tool hooks. An `unownedTurn` reply cannot borrow the current turn to update its estimate. `SessionActivity.currentProgress` keeps the latest estimate of the current turn, including a lower one.

The ring follows the request, not the turn. A typed prompt starts a request; turns started by task notifications, scheduled wakes or other sessions (`source` other than `user`/`sdk`, or a prompt opening with a notification tag while Claude Code omits `source`) continue it, carry its estimate to the new turn and get no second line; `SessionStart` with source `compact` adds the line again. At `Stop`, any `background_tasks` entry other than a long-lived monitor or Claude Code's own memory and scan work (types `monitor`, `dream`, `auto-mode scan`, `memory import`, `memory save`), or any `session_crons` entry, makes the adapter write a nonempty `waiting` snapshot. A later Stop with no background work writes an empty snapshot to clear an earlier attempted wait. Unlabelled kinds such as a PowerShell background command count. `ClaudeActivityState` then keeps the turn running instead of completing it, so no completion is announced until the request really ends; the row shows the `background` task symbol (glyph `zzz`) and the status `activity.background_wait` until the wake. Newer model output or a new tool start in the same turn clears the wait, so another Stop hook can continue work without suppressing its final verified ending. Waiting snapshots and clears use their own timestamp, which resets with the turn and never advances `lastObserved`. A delayed final transcript response can still apply after its later Stop snapshot was read from the spool. Older nonempty waiting snapshots cannot restore a cleared wait, and older clears cannot erase newer background work. An interrupted or failed request retains its estimate on the ending card, but neither its wait nor its estimate carries into a new request. Without such work the stop ends the request and is never held for a final estimate; `pacer/progress-state.json` only records which sessions have the plugin. `TaskProgressRing` reports a lifecycle `mode`: `working`, `longStep` (a tool running 30 seconds or more), `attention`, `waiting`, `done`, `interrupted` or `failed`. Only `working` fades after 120 seconds without an estimate; an active request without one shows the dashed `pending` ring. A normal ending is `done` and fills the ring to 100% whatever the last estimate was, with or without one; an interrupted or failed request keeps its last estimate and shows no ring without one. Windows draws it around the 28-pt status icon (the icon shrinks from 20 to 16 pt): the dashes turn while working or in a long step, a light dot runs along a working arc, a waiting arc breathes (opacity 100% to 20% over 2.4 seconds), and an ending sweeps the arc from its current value to full, easing out of a breath if it was waiting. Interrupted motion resumes across row rebuilds from the old ring's actual WPF clock time, including the sine curve used for a lowered estimate and the delay before a completion sweep. `CurrentTimeInvalidated` calibrates the remembered start because WPF may start a clock at a time manager tick that predates `Show`. Remembered rows hold only a weak lease reference, and a replaced clock cannot recalibrate its successor's timeline. Reduced motion settles a finite sweep at its target immediately. Looping motion starts only after a row's ring is fully shown, and its endless clocks are leased (`AnimationLease`), so a discarded row leaves no clock ticking. Presentation checks load real rings into a window, remove them without calling `Halt`, and assert that `Unloaded` releases the looping clocks and property animations. They also compare displayed fractions across consecutive downward-estimate rebuilds with 90 ms and 170 ms UI thread stalls and a controlled 45 ms WPF clock lead. The continuity bound remains 0.06. Run these checks alone with `pwsh -NoProfile -File scripts/windows/test-presentation.ps1 -Configuration Release -Group progress`. The Mac draws the same ring with Core Animation in `TaskProgressRingNSView`. Sweeps are keyframes sampled from the curve its per-task memory evaluates, so a row rebuilt by paging or reopening the panel resumes from the displayed value; the turning dashes, the dot and the breath are phase-locked to the media clock. Loops run only while the row's window is visible and unoccluded, and reduced motion or a hidden panel settles every ring at its final value. A row's width probe draws no ring. `IslandModel` writes the switch with the same ownership rules and runs one hook setup at a time, so switching the ring never edits Claude's settings alongside a source start. SSH and WSL hosts get the same ring: `ClaudeRemoteSetup` passes `progressRing` (and, when on, `claude_progress_mcp.py`) to the remote installer, which writes the switch file and Pacer's plugin under the remote `pacer` folder with `python3` as the server command and adds or removes exactly the same settings entries. The remote adapter digest includes the ring state, so switching it sets connected hosts up again. The read-only helper forwards `progress` and `waiting` rows and a prompt's `wake` flag, keeping only the integer estimate, up to 16 task kinds of 24 characters, a wake-up count of 0–16 and `wake: true`. Claude cloud Project threads cannot run the plugin, and a poll identifies their run only when it ends, so `TaskProgressRing` marks them `cloud`: while running or waiting for the user they keep the dashed ring without a turn ID (`activity.progress_cloud` in hover and accessibility text), and a completed run fills it like any normal ending. The dashes stop where they are when a ring ends, so they close in place before the arc sweeps to full.

Hook and status-line commands run `python3 -S`: the adapter uses only the standard library, so skipping site-packages avoids `.pth` processing in conda-style installations. `-E`/`-I` are avoided because macOS's bundled Python then recompiles its standard library on every call. It loads slower modules only on the paths that need them, rewrites hook state in place under the spool lock, repeats display metadata only when it changes or a turn begins, and rewrites an unchanged status-line sample at most every 30 seconds. Each Claude source start brings the installation current: an outdated adapter and Pacer-owned legacy entries are migrated in place, optional environment values or wrappers the user removed stay removed, and missing required hooks are restored while the module is on. The automatic setup adds Pacer command hooks, installs a status-line wrapper that passes the original stdin/output through to an existing renderer, and stores sanitized quota/lifecycle records beneath the selected Claude home's `pacer` directory. It adds beta OTLP trace settings for `127.0.0.1:4319` only when existing tracing settings/headers do not conflict. Conflicting telemetry is preserved, and Pacer then reports no request metrics. New Claude Code sessions must load the changed settings. Local project-directory metadata may be retained for navigation; it does not leave the host. A direct Desktop continuation URL requires a verified `local_UUID` mapping from the active Desktop account; SSH mappings additionally match the canonical host/user/port route. Default Desktop metadata cannot establish ownership of a separately selected local Claude profile. An observed Claude child can route through a validated parent UUID or a bounded, observed same-provider/host/source ancestor chain to a UUID root, even when the parent card is absent. The same Desktop metadata or profile/SSH resume checks still apply; the child's directory or Desktop ID never establishes the ancestor's path or continuation URL. Without a verified mapping, local UUID sessions open a real Terminal TTY with an explicitly quoted `CLAUDE_CONFIG_DIR` for the selected home. The installed CLI uses `--desktop --resume` only for the default profile with Desktop present, and `--resume` for custom profiles or CLI-only use. SSH fallback opens a validated SSH TTY resume command. Opening supplies no prompt and does not create a turn. The actual open outcome determines acknowledgment: successful verified conversation handoff dismisses the matching captured ending and any eligible captured terminal descendants described below; Terminal dispatch or failure preserves them because launch success alone does not confirm that the conversation opened. A queued open from a replaced source is discarded before dispatch.

Claude SSH targets combine enabled discovered Codex hosts with Claude Desktop’s `ssh_configs.json` and `sshConfigs` in the selected Claude home’s `settings.json`. These client-owned files are read-only; host additions/removals follow the existing discovery cadence or an explicit refresh. User settings override a Desktop config with the same ID. Canonical SSH host/user/port routing deduplicates both clients while preserving existing Codex source IDs. Claude-only direct destinations use bounded hashed source IDs, their saved port and identity-file path; no key contents are read. Route lookups use `ssh -G`, reuse results for up to five minutes with SSH config signature invalidation, and never establish connectivity. At most eight sources are monitored, with existing Codex hosts first. The former `claudeSSHHosts` preference is ignored and removed on the next Settings change. Changing or removing a discovered target cancels only its owned collector/setup work. A reachable host without a Claude home is shown as a paused missing source rather than an SSH failure. Its running/attention state becomes unconfirmed, its completed cards remain, and its released helper no longer counts as a live connection. Routine discovery retries after 30 minutes; successful remote setup and explicit refresh bypass that source's backoff immediately while preserving healthy helpers. Target reconciliation publishes only when targets or connections change, and Codex global state is reparsed only when its file signature changes. They use existing SSH authentication and known host keys. Owned Python 3.6+ helpers sanitize data on the host, retain separate provider state, and exit on owner stdin EOF or broken stdout. The remote helper is read-only. Hooks/telemetry come from `ClaudeRemoteSetup`, which the island runs automatically whenever SSH monitoring and the Claude module are on, for each connected host that has a Claude home and whose recorded adapter digest (`claudeRemoteSetupDigests`, keyed by alias) differs from the shipped installer and hook. The installer never creates a Claude home in this path, rewrites only changed files, and a failed host retries after 30 minutes. Turning Claude or SSH monitoring off, replacing its source, sleep and quit cancel the owned in-flight installer; a discarded request neither records success nor adds a failure/backoff to the new source. Running remote sessions pick up newly added hooks after a restart. Local setup does not establish that remote configuration is present. Per-provider status and unavailable-source reporting remain independent.

Claude SSH pipe delivery uses `PipeChunkReader` readiness callbacks and a bounded `AsyncStream`, rearmed after actor consumption to retain ordered backpressure. The SSH helper and the native reader both order the owned hook spool before transcript cursors during cold replay and simultaneous dirty appends: while the spool still has complete records beyond a read's 512-line bound, transcripts wait for the next read instead of being correlated against an older hook turn. Prompt ownership can therefore precede engine continuation and clean-stop records instead of a later hook start reviving an ended turn. Exact prompt/parent links and explicit terminal evidence remain required; ordering adds no silence or timeout heuristic. A quiet pipe does not occupy a Swift cooperative worker while waiting for data. Source-status frames publish immediately; ordinary numeric updates retain visibility-based batching. EOF, cancellation and reconnect release only the owned reader/helper, preserving the other provider's transport.

### Claude cloud Projects

A Claude Project is a cloud channel (`chan_…`). Its threads (`cmsg_…`) bind one or more cloud sessions, and its overview session is the coordinator that answers the main conversation and routes work. `ClaudeCloudProjectMonitor` reads them with the session from Pacer's dedicated `WKWebsiteDataStore`, the one quota reads use: `GET /v1/code/channels?limit=50&scope=joined`, `GET /v1/code/channels/{id}/threads?limit=20`, `GET /v1/code/sessions/{id}` and `GET /v1/code/sessions/{id}/events?limit=8` on `https://claude.ai`, with the `ccr` client headers, an ephemeral redirect-rejecting `URLSession` and a 4 MiB reply limit. These endpoints are private and version sensitive. Pacer sends nothing to them and still reads no other app's token or Keychain item. `--diagnose-claude-cloud` prints counts and status names only, including how many recent threads report a speed, for checking them after a Claude update.

`ClaudeCloudDecoder` keeps lifecycle fields and a finished turn's numbers. Thread rows also carry message `body` and `thread_preview`, sessions carry tool input and events carry message text; none of these leave the decoder. A pending tool is reduced to question or approval by comparing its name with `AskUserQuestion`.

Pacer polls: `/v1/code/sessions/watch` answered 404 `endpoint not enabled` and `/v1/code/notifications` 501 when this was built (Claude's web client gates that feed per account), and `/v1/code/sessions` lists Desktop's local sessions rather than project threads. The web client's message streams add only an early start and an estimated speed, as described under Streams. `ClaudeCloudPolling` looks every 20 seconds while something runs, 30 while the panel is open or a project or thread just changed and up to 120 otherwise, doubling from 30 seconds to 15 minutes on failure and honoring `Retry-After`. A 404 or 501 on the list means the account is not offered Projects: the source stays hidden and is tried again after 30 minutes. A rejected session pauses the source until a new sign-in. Reads recheck the session and selected organization after asynchronous work; refresh and suspension invalidate outstanding reads and stream callbacks. Changed accounts do not inherit the previous account's backoff. Only the 16 most recently active projects are followed; a project quiet for three days is reread every 10 minutes. A pass reads at most 16 sessions, rotating least recently attempted candidates so a busy account cannot permanently occupy every slot. Ties put open rows and waiting threads first, then coordinators, then threads under 24 hours old that moved, have just ended, or are idle and have not been looked at for two minutes, since answering an idle thread moves nothing on its row until the first reply. Sleep suspends the loop but keeps the state, because cloud work continues and its ending is still worth reporting on wake.

`ClaudeCloudProjectState` projects each pass through the shared activity events, under the single source ID `claude-cloud`, so `CompletionInbox`, `AttentionPolicy` and task groups need no cloud branch. A thread row's session is its `cmsg_…` ID and a coordinator row's is its session ID.

The states below were observed live against a real project in Claude Desktop's 2026-11 service. The thread row goes quiet within seconds of a run starting, so it cannot say whether work is in progress:

| Thread row | Session | Pacer |
| --- | --- | --- |
| `working` or `thread_any_session_working` | any | running, `working` stage |
| `idle` | `status_bucket` `working` on a live connection (`worker_status` reads `idle` or unspecified during a long tool call) | running |
| `idle` | stopped, no `post_turn_summary.status_category` or `blocked`/`need_input`/`waiting` | ended, "Reply needed" |
| `idle` | stopped, any other category | ended, "Turn finished" |
| `resolved` | any | ended, "Resolved" |
| `needs_input` (`status_bucket` `blocked`, category `need_input`: Claude asked in plain text) | stopped | waiting for a reply, until read |
| any | `requires_action` | waiting for a reply or approval, until answered |
| `open_decisions` not empty | | waiting, separate `decision` kind |
| `failed` | | interruption with `turnFailed` |
| `archived` | | row removed |

Unknown statuses read as idle, as in Claude's own client, and a running session on a dropped connection counts as stopped. The reply-needed rule is the web client's own (`status_category` undefined, or one that asks for the user, makes a stopped turn `needs_input`). The summary arrives seconds after the turn stops, so an idle ending keeps being read for a minute and its label can change. An inline decision card leaves the thread `idle` with an empty `open_decisions` and no summary, so it ends as "Reply needed", and choosing an option starts the same thread again. A plain-text question that was read and left unanswered stops asking: the row is dropped once `has_unread` clears, or after 90 seconds if it never rose, and on the first pass it needs unread and under seven days. `requires_action` was not reached live because project sessions run with `permission_mode: auto`, so that row is covered by tests only. An open row missing a bound session's state keeps its last confirmed run for up to five minutes, then becomes unconfirmed until fresh evidence arrives; a skipped or unreadable session cannot establish completion.

The first pass is a baseline: running threads attach, unread endings from the last seven days become quiet historical cards, and everything else stays out. A short run can fall between polls, so a later ending is also recognized from a newer `last_reply_at` on a thread that is unread or whose session has stopped, or from a coordinator's unread flag rising. An ending's in-memory turn ID comes from its first observed reply time. `idle` can precede `resolved` for the same thread with a newer reply: within five minutes this only updates the label, so one run reminds once. Persistent dismissal uses the latest reply marker, and up to 128 acknowledged idle endings retain only a hashed source identity and timestamp to bridge that same settlement across relaunches, including when resolved arrives while Pacer is closed. An observed new run revokes the pending settlement acknowledgment. Turning off Show Claude cloud Projects hides retained cards and requests without acknowledging them; turning it back on restores still-retained unread cards. After three failed passes open rows become unconfirmed, and the next pass ends or resumes them.

**Coordinator.** The overview session runs with the `coordinating` stage. A turn that is about threads is not news of its own and its row is dropped without an ending: a thread is open, a thread was created during the turn, or a thread ended within two minutes of it (the follow-up report). Threads are applied first so this sees their current state. `status_bucket` `blocked` with category `need_input` cannot tell these apart from a direct question, because the summary also says so when a thread is the one asking. A turn that answers on its own ends with a card, worded "Reply needed" when it asked.

**Read state.** A thread's `has_unread` is the signal: it rises at `resolved`, about 24 seconds after the ending, and clears when the thread is opened. An idle thread never raises it, and `session.unread` stays true on thread sessions even after opening them, so neither says anything about an idle ending. Its card stays until it is clicked or a new run replaces it, and an idle thread makes no baseline card. Elsewhere `readInClaude` needs either unread seen and then cleared, or 90 seconds without it; the coordinator uses `session.unread`, which does clear. `combineActivities` dismisses such a card, which also persists it.

**Streams.** `ClaudeCloudReplyStreams` reads the web client's SSE at `/v1/code/channels/{id}/messages/stream?from=tail&caught_up=true`; `from=tail` skips the project's history (6.5 KB on connect against 158 KB), and a keepalive comes about every 14 seconds. Polling still decides every state, so a lost stream only loses a speed. Each of the four most recently active projects (active within three days, or with open work) keeps one stream, which carries the project's messages, `thread_starting`, `session_activity` and the coordinator's own partial replies but not its threads'. Each running thread gets its own with `scope=thread&thread_id={id}`, at most six, kept for 90 seconds after it stops running. A connection receives only replies that start after it connects, so the project's stream is what makes this work: in a measured new thread `thread_starting` came 8.4 seconds and `session_activity` (`working: true` with a `thread_root_id`) 7.1 seconds before the first partial reply, and the thread's stream opened in 0.3 seconds and caught it from its first characters. A thread stream opened later, after a poll or a drop, misses the reply underway and picks up at the next one. The same signals bring the next poll forward, at most once per 5 seconds: a new thread's row appeared 7–11 seconds after the message that started it, because the coordinator takes that long to open it, and a follow-up's in 2. The parser decodes only those three events, leaves message bodies unread, and reduces partial text to a number before returning. A refused stream waits 15 minutes, a dropped one backs off from 5 seconds to 5 minutes, and one the server ended after at least 30 seconds comes back after 2. `--diagnose-claude-cloud` reports whether the stream opens. Windows reads these streams and the cloud polling through WinHTTP rather than URLSession, because a FoundationNetworking request keeps a thread busy until its response ends ([HTTP through WinHTTP](windows-engine.md#http-through-winhttp)).

**Speed.** No token count is published during a run: `external_metadata.usage` stays empty until the turn ends, and assistant events carry a stale `usage.output_tokens` (5, 25 and 32 in a turn that output 1860). So a running thread's speed is an estimate. `session_partial_reply` (`text`, the whole reply so far; `tool_use_id`) arrives about every 0.44 s, and `ClaudeCloudReplyMeter` converts its growth at 1.09 tokens per CJK character and 0.3 per other character, from turn results of 84.7 t/s at 78 characters a second in Chinese and 84–99 t/s at about 305 in English. In three live runs through Pacer it read 83–88 against a real 88.1 (English), 71–87 against 82.9 (Chinese, with a `sleep 20`) and 77–84 against 85.0 (an English follow-up). Expect about ±15%; code is unmeasured. It averages the last 10 seconds of writing and needs 2 seconds of it; a pause over 3 seconds is not writing, and thinking and other tool calls never appear in a partial reply. The estimate goes stale after 15 seconds like any rate, joins the header total while the thread runs, and never reaches an ending. Repeating the text is what this costs: 84 KB for a 600-word reply and an estimated 4–5 MB for 8,000 Chinese characters. After a thread ends, the events reply lists the newest first, and its `result` event gives `usage.output_tokens`, `process_wall_ms_streaming` and `ttft_ms`. Their ratio is one `requestUsage` sample for the turn. It measured 67–95 t/s across seven threads against 76–92 on local rows, and a `sleep 20` in the turn did not lower it. It is a turn average without the wait for first output, so it reads slightly above a local request. `duration_api_ms` must not be used because it adds up across a session's turns: one thread read 12 t/s that way. The coordinator's `result` has no `process_wall_*` fields, and its replies are too short to measure, so it shows no speed. A new run starts without a value, so an earlier turn's cannot read as live. The result can land after the thread reads as ended, so up to three passes look for one newer than the run's start and not already used, with at most four lookups a pass.

Polls cannot date a run's start, so elapsed time counts from when it was first seen, and a late look stamps the ending when it was noticed so its reminder still fires; `AttentionPolicy` only announces endings under a minute old. A thread whose every bound session matches Desktop's `bridgeSessionIds` or `remoteControlSpawn.ccrSessionId` is left to the local reader. Project tools run through the Desktop bridge on the user's Mac, so a test prompt in a project runs commands locally. `IslandModel.makeClaudeCloudMonitor` is set by the app only, so tests and demos never reach claude.ai.

### Codex sessions from other apps

**Classification.** A rollout's `session_meta.originator` names the client that started it. `source` cannot tell them apart: Codex Desktop and the Zotero ACP bridge both report `vscode`. `CodexSessionOrigin` keeps the official-client list, checked against the [Codex 0.162.1 first-party definitions](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/login/src/auth/default_client.rs) plus Desktop's `Codex Desktop`; current TUI sessions use `codex-tui`. Any other originator marks the session as embedded, and a missing one leaves it unclassified. Only two booleans, `embedded` and `ignoredSession`, leave the parser; the originator string is never stored or forwarded. A newer launch record in the same rollout wins, so a thread later resumed by an official client is no longer embedded. Subagents take their parent's classification (same provider and host) without changing the reader's baseline. The SSH helpers run Python generated from the same list.

**Zotero translations.** Zotero Agent 0.14.0 runs translations through its Codex ACP bridge, which ignores the plugin's `ephemeral` flag, so they leave rollouts. An embedded session whose cwd ends in `zotero-chat/translate`, or whose last path component starts with `zotero-chat-catalog.` (the plugin's model-list probe), is ignored regardless of settings. Ignored sessions and their subagents create no task, completion card, notice or first-output and rate measurement.

| Entry point | Handling |
| --- | --- |
| Local rollout reader | Classifies up to 256 candidate headers, plus a bounded 128 KiB tail, before choosing cursors and watches, so ignored sessions use no slots. The header read for the cursor is reused, and tail rows without `"session_meta"` are skipped before parsing. A changed ignored file is rechecked, so an official resume shows up. Excluded IDs are returned separately, so retained cards are dropped without being acknowledged. |
| Local and SSH app-server helper | Reads bounded metadata under the selected home before any `thread/resume`. Ignored threads never get a subscription, and are rechecked if an official client resumes them. |
| SSH log fallback and accounting | Adds the two booleans to sanitized metadata and resolves parents before choosing slots. Ignored sessions never reach snapshots or counters. |
| Codex Desktop IPC | Checks local metadata before following a local thread, and resolves its parent without subscribing to it. |
| Remote Control | Unchanged. Local rollouts never classify a remote task, even one with the same UUID. |

**Finding the app.** Codex has no session registry like Claude's. Pacer looks for the same-user process that holds the rollout open for writing (`proc_listpids`, `PROC_PIDLISTFDS`, `PROC_PIDFDVNODEPATHINFO`) and walks up at most 32 parents to the first regular app. It never reads process arguments or environment variables, and process start times guard against PID reuse. With Zotero Agent and Codex 0.159.3, the bridge's app-server kept the rollout open in all 60 idle samples taken after a request. A scan covers at most 2,048 processes with 4,096 descriptors each; on a Mac with about 850 processes it took about 14 ms of CPU. Scans run at most every two seconds per provider, and only while a local embedded session is known. A found app is remembered while the row or its completion card remains. The scan lifecycle is shared with Claude (`ProcessOwnership`, `HostApplication`, `HostApplicationTracking`): sleep, source changes and quit cancel scans and retries, and scan IDs reject late results.

**Opening.** Clicking a local embedded Codex card looks for the current holder, then activates that app or the remembered one, relaunching it if it quit. Success acknowledges the captured ending and eligible captured subagents. Pacer can only learn the app while the session runs; if it never saw it, the click says so for 30 seconds and the card stays unread. If the remembered app was moved or deleted, the message names it. This path never opens `codex://threads`. Official Codex clients and SSH tasks open as before.

**Visibility.** `showEmbeddedCodexSessions` and `showEmbeddedClaudeSessions` default to on and only filter what is displayed and announced, using the current reader snapshots plus retained completion cards. Hidden turns are still collected and expire normally without being acknowledged. Each provider has its own switch in Settings. The 3.1.2 update note shows one switch that sets both and reads on only when both are on; fresh installs see the welcome guide instead.

### Codex accounting and lifecycle

Codex and Claude have independent progress-ring settings, both off by default. The Codex ring uses the existing Windows and Mac renderers. An active task can show a dashed ring before a report arrives. A confirmed request ending fills it; interrupted or failed requests keep their last estimate. A working report of 100% can fill the numeric arc without playing the completion pulse. Only the transition to a confirmed ending plays that pulse for Codex.

[Codex progress reporting](codex-progress-setup.md) uses a stdio MCP mode in the Pacer executable. The local switch schedules registration for the selected Codex home. Pacer reads the user layer and uses the returned version to update only `mcp_servers.pacer_progress` through Codex's app-server. A conflicting entry stays in place. A local flag lets an already-connected reporter stop accepting calls after disable. The MCP server advertises its guidance in the tool description and initialization response. Pacer accepts successful calls from the active turn's rollout or runtime stream and correlates legacy calls with their responses. Only the estimate and bounded ownership metadata enter the projection.

Codex distinguishes a terminal rollout error from a successful turn and tracks outstanding tools, waits and blocking flags separately. Async questions can change the ring style while a tool keeps running. A goal bound to the current request can keep it open between turns, with a static pause or limit state when applicable. Verified continuations carry their estimate and its original timestamp. A terminal event from one transport can arrive before its rollout record; a goal already bound by the matching source keeps that attempt's ending from filling the ring. Missing linkage limits display to the observed turn. See the [state and animation mapping](codex-task-state-animation.zh-CN.md) and the [design and source evidence](codex-progress-ring.md).

Run `scripts/diagnostics/test-codex-progress.py` with the installed Codex executable and the built Windows desktop engine. A disposable profile and loopback model exercise automatic MCP setup, tool guidance, percentage revisions, the terminal outcome and cleanup. `--client app-server` starts Codex before registration and opens a new session after setup. The Windows `progress` and `settings` presentation groups check the ring and its switch in WPF.

Available credits are deduplicated, grouped by exact expiry and sorted earliest first, including deadlines beyond the displayed weekly curve. ### DeepSeek Harness

Harness writes each session to `$DSH_HOME` or `~/.dsh`, under `sessions/<workspace>/<session>/session.v4.jsonl.zstd`: concatenated checksummed Zstandard frames, one per appended batch, flushed before the next. `DeepSeekSessionReader` discovers at most 64 workspaces, 2,048 session directories and 256 logs modified in the last eight days, reads only whole frames from a cursor (a torn tail waits, a frame failing its checksum is skipped whole, and undecodable data skips to the log's current end), reads up to 32 MiB of compressed input per pass and retries one larger frame once at 64 MiB. Each decoder call bounds decompressed output and the Zstandard window to 64 MiB. The output limit applies inside a frame even when its content size is unknown: a frame exceeding the full limit is discarded whole, while a valid frame that only exceeds the remaining allowance waits for the next pass. Following frames remain readable. `stat` supplies size and modification time so appended frames are never hidden by cached resource values. Watches cover the root, three recent workspaces and 28 logs. Each frame’s compressed offset determines whether it belongs to the captured startup baseline, so frames appended during catch-up keep their live timing and completion reminders. A frame partly written at startup stays historical when it finishes; following whole frames are live. Baseline lines are classified by their leading `"type":"` and only `turn/start`, `turn/end`, step, tool, approval, model and the usage of `assistant/message` are projected, via light paths that never materialize message text, reasoning or tool arguments; lines over 4 MiB are dropped. Only header version 4 is accepted.

`DeepSeekActivityState` maps the events onto `SessionActivity.applyRuntime`: `turn/start` starts a turn (`turn/attached` while attaching), `step/start` is thinking, a `tool/call` is a running tool, `approval/asked` without its `approval/decided` raises an approval request, an unanswered `ask_user_question` tool call raises a reply request, and `turn/end.reason.kind` is `completed`, `error` (failed) or otherwise interrupted. Turn IDs are the turn number plus the starting sequence. Each `assistant/message` carries `usage` (`inputTokens` without cache, `cacheReadTokens`, `outputTokens`) and stream chunk times: its `ResponsePerformance` spans the request (the step start or the previous tool result) to the last chunk, and time to first output is reported only for the first response of a turn. Harness writes a response only when its step ends, so stage, speed and cost settle per step; while a step streams, the bar keeps the previous measurement in the secondary color. A running baseline turn becomes unconfirmed when no process holds the session's `session.lock` open for writing, checked with the same descriptor scan as Codex rollouts and only for open turns; the one-minute maintenance pass repeats that check for quiet live turns.

Cost is estimated locally from the tokens and `DeepSeekPricing` (CNY per million tokens: `deepseek-flash` 0.02 cache hit, 1 miss, 4 output; `deepseek-v4-pro` 0.15, 4.5, 13.5), doubled on Beijing weekdays 09:00–12:00 and 14:00–18:00. Weekends and the State Council's 2026 public holidays are off-peak; make-up working days on weekends count as weekends, and later years have no calendar yet, so peak hours are an estimate. Tool calls named `web_search`, `web_fetch`, `search` or `fetch` add ¥0.005 each from 2026-11-01 (Beijing). Only Harness's own providers (`deepseek`, `deepseek-account`, `deepseek-official`, `deepseek-api-key`, or none reported) are priced; a third-party channel gets no estimate. Unknown models have no cost. Each response is recorded once by its ID in an eight-day `DeepSeekSpendLedger` with its root session: a delegated session's `parentSession` chain (at most eight levels) makes sub-agent spend count toward the root task. Entries keep their originating session and turn; late ancestor headers resolve earlier entries again, and a parent turn includes delegated charges only inside its observed start/end times, independently of log replay order. The ledger yields today's total and peak share, hourly spend, per-task totals, twelve 10-minute spans, the usual spend by this time over the previous seven days, a daily average and the last seven days. `SessionActivity.turnCost` and `turnPeakCost` hold the current turn's sum and survive merging only for the same turn; Settings → DeepSeek → Show each turn's estimated cost (`deepseekShowsTurnCost`, default on) shows it before the model name as `≈¥0.42`, with an amber dot when part of the turn was billed at peak and a tooltip giving the task's spend today, its peak share and sub-agent count.

## Persistence and verification

Remote Control acknowledgment binds to device routes published by the monitor with each activity update, before processing that update's endings. A verified paired-device catalog takes precedence over saved discovery hints; a temporary loss of connection status or a pending catalog after transport restart does not remove known source bindings. Catalog-confirmed device removal invalidates an awaited open even if an older saved route remains. Source-home or module changes clear the monitor-derived set before rebinding, and names/online flags do not change acknowledgment identity.

The production bundle is `com.codexpacer.app`. Successful verified conversation opens persist up to 512 acknowledgment hashes in an atomic, owner-only file, so the same ending stays dismissed after normal relaunch. Opening a terminal parent also acknowledges only eligible descendant endings captured at that click: the child and its bounded ancestor chain must already be terminal, share the provider/host/source and still match their captured turn, start and ending states after the asynchronous open returns. The hashes distinguish providers, local homes, configured host homes, sessions, explicit turns and ending states; legacy turns without an ID also include normalized start/end times. ## Continuous integration

`.github/workflows/platforms.yml` tests each change once, on its pull request into develop. `.github/workflows/release.yml` builds, signs and publishes a tagged release.

- **Pull request into develop.** Only the platforms the change touches run. `scripts/ci/changed-platforms.py` decides this from the changed files:
  - Shared Core, the root package, `native/Info.plist`, the workflow and unknown files run both platforms.
  - Mac-only and Windows-only paths run only their platform.
  - Documentation runs nothing.
  - The platform contract, its tests, the shared localization check and the DeepSeek web identity check run once on Linux for every run.
  - The Mac suite runs on Apple silicon.
  - Windows x64 compiles the shared engine and runs its tests in one job. Another job builds the release engine and desktop once. Three jobs then share that build for the desktop, Claude runtime, presentation and idle checks; none of them installs the Swift toolchain. ARM64 compiles only.
  - `test-presentation.ps1 -Group` takes a list of groups. Each group that `all` runs is in exactly one of the three test jobs, and `scripts/windows/check-contract.py` checks this against the runner's `AllGroups`.
  - The release engine and its two adapters are cached per architecture. The key is the engine source snapshot from `stage-engine.py`, plus the toolchain lock and the build scripts. On a hit, `build-engine.ps1 -Products` copies them instead of compiling. GitHub limits a pull request's caches to that pull request and its base branch, so a pull request hits either an earlier run of its own with the same engine sources, or what the develop warm-up saved.
  - The Windows package smoke test and the installer and patch lifecycle run in their own job when the change touches what the installers are built from or what those checks start: the installer, maintenance, update and hook projects, the packaging scripts, the toolchain pins, the workflow, and the app's launch, single-instance, installation identity, notification and startup registration code.
  - A newer push cancels the pull request's older run.
- **Push to develop.** Only `.github/workflows/engine-cache.yml` can run, and only when the push changes what the engine cache key covers. For each architecture it looks the key up and ends there when it is cached; otherwise it builds the release engine and its adapters once and saves them, so the next pull requests start with a hit. It tests nothing. `scripts/windows/check-contract.py` keeps its path filter and key in step with the snapshot and the other caches.
- **Push to main or a promotion pull request into main.** Nothing runs.
- **Manual Platforms run.** Runs every test job, on any branch.
- **Release tag (`vVERSION`).** The code is what develop already tested, so `release.yml` tests nothing again. [The release](releasing.md) workflow:
  - builds the Windows installers: x64 with its package smoke test, and ARM64 without running it;
  - builds, signs and notarizes the universal Mac DMG, which compiles both Mac architectures;
  - signs both update feeds and publishes the GitHub Release.

  Its Windows jobs hold no secrets; only the Mac and publish jobs use the `release` environment, and `scripts/windows/check-contract.py` keeps it that way. A release run is never cancelled. A manual run does everything except publishing.

## Performance checks

The event benchmark compares the embedded Desktop IPC projection from two source trees with identical synthetic patches. It checks projected state and emitted events for equivalence, excluding wall-clock timestamps, and alternates execution order. To compare an uncommitted change against the current commit:

```sh
task_baseline="$(mktemp -d /private/tmp/pacer-baseline.XXXXXX)"
git archive HEAD native | tar -x -C "$task_baseline"
python3 scripts/performance/benchmark-events.py \
  --baseline "$task_baseline" --candidate . \
  --output output/performance/events.json
```

Use the intended baseline ref instead of `HEAD` for committed changes. Results measure component CPU cost, not whole-app speed, memory, energy or SSH I/O. Keep raw results under ignored `output/`; profile the current packaged app for UI measurements. [Historical measurements and their replay harness](https://github.com/RyanZhangNTU/codex-pacer/blob/v2.1.3/docs/performance.md) remain in tagged source, but that UI harness predates the current app packaging and is no longer maintained.

Live UI measurements need a verified candidate PID, current unlocked-machine state and fresh main-panel checks at the interval boundaries. Unknown lock timing or potentially stale UI frames leave a window UI-unconfirmed and exclude it from visible collapsed/expanded comparisons. Record active task/source changes and concurrent windows; an active run is not isolated idle. Per-process CPU and short-window OS energy counters apply only to their captured process set, with partial descendant coverage during reconnects; they do not measure WindowServer, GPU, remote helpers or whole-system power.

For explicitly authorized local troubleshooting, set the production preference `pacerLocalRuntimeTrace` to true before launch. The Mac process writes at most 1 MiB to a private `/private/tmp/pacer-runtime-trace-PID.jsonl` file containing hashed routing identifiers, lifecycle methods, phases and timestamps. It excludes task text, paths, requests and token values, and adds no remote diagnostic code. Delete the preference and relaunch after diagnosis. Normal launches do not create or write this trace.
